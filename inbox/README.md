# inbox — 待整理区

你发来的零碎知识点先落到这里，**原文一字不改**，整理完再归档。

## 为什么要有这一层

零散知识点的最大风险不是写得乱，是**丢**。会话一过就找不回来。
所以规则是：先落地，再整理，绝不直接在正文里改。

## 一条笔记的格式

不用你排版，我自己生成。落地后长这样：

```markdown
---
date: 2026-11-13
source: chat
status: inbox          # inbox | merged | conflict | dropped
target:                # 整理进哪一章，如 05-交付与发布.md
---

## 原始输入

[用户原话，一字不改，包括口语和错别字]

## 我的理解

[一句话提炼成什么概念]

## 归属判断

- 属于：[章节名] 的 [哪一节]
- 理由：
- 与现有内容：新增 / 补充 / **冲突**
```

## 状态说明

| 状态 | 含义 | 后续 |
|------|------|------|
| `inbox` | 刚落库，未处理 | 下次整理时处理 |
| `merged` | 已并入正文，原文移到 `archive/` | 保留可追溯 |
| `conflict` | 与现有观点矛盾，**未改动正文** | 等你确认哪个对 |
| `dropped` | 判断为不成立/不适用 | 记下原因，不删 |

## 三条纪律

1. **原文永不删改。** 你的原话是判断依据，改了就失去可追溯性。和你现在的用词也是素材——同一个概念你怎么描述，比标准说法更能帮你记住。
2. **冲突不覆盖。** 新知识点和现有章节打架时，我只标注 `⚠️ 冲突`，把两种说法并列，等你定。我不会默认新的对。
3. **不硬塞。** 如果一条知识在 12 章里找不到合适位置，我先攒在 `inbox/pending.md`，同类攒到 3 条以上再考虑独立成章。宁可晚整理，不做强行归类。

## 归档

整理完成后，笔记文件移到 `inbox/archive/YYYY-MM/`，frontmatter 的 `status` 和 `target` 填好。这样任何时候都能回答"这条我当时是怎么说的、被放到哪了"。
